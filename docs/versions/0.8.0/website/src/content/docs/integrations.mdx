Innov detects supported agents automatically. Official integrations can add native session identity for restore, lifecycle state reports, or both.

Use integrations when you want native agent session restore, direct lifecycle reports, or both. See [Agents](/docs/agents/) for the full status authority model.

## Install integrations

Open settings inside Innov and use the integrations tab to install recommended integrations for agents found on your `PATH`, or run commands manually:

```bash
innov integration install pi
innov integration install omp
innov integration install claude
innov integration install codex
innov integration install copilot
innov integration install devin
innov integration install droid
innov integration install kimi
innov integration install opencode
innov integration install kilo
innov integration install hermes
innov integration install qodercli
innov integration install cursor
innov integration install mastracode
innov integration install antigravity-cli
innov integration install grok
```

## How Innov uses integrations

Innov uses integrations in two different ways:

| Integration type | Agents | Effect |
| --- | --- | --- |
| Lifecycle authority | Pi, OMP, Kimi Code CLI, OpenCode, Kilo Code CLI, MastraCode | When installed and actively reporting for the pane, hook or plugin events author `idle`, `working`, and `blocked`. Innov does not also use screen manifest fallback for that same lifecycle authority. |
| Session identity | Claude Code, Codex, GitHub Copilot CLI, Devin CLI, Droid, Qoder CLI, Cursor Agent CLI, Hermes Agent, Antigravity CLI, Grok CLI | The integration reports native session references for restore. State still comes from Innov's screen manifest detection. |

Custom integrations can also report state when they define state that is not visible in the native terminal UI. They do not need to be built into Innov or use a recognized agent executable.

## Integrate your own agent

An agent running in a Innov pane inherits `INNOV_ENV`, `INNOV_PANE_ID`, `INNOV_BIN_PATH`, and `INNOV_SOCKET_PATH`. If the agent exposes lifecycle hooks, use those hooks to report semantic state through Innov's CLI:

```bash
"$INNOV_BIN_PATH" pane report-agent "$INNOV_PANE_ID" \
  --source custom:my-agent \
  --agent my-agent \
  --state working
```

Report `idle` when the agent is ready for input and `blocked` when it needs a user decision. Use `--message` to describe a block. When the agent exits, release the same source's lifecycle authority:

```bash
"$INNOV_BIN_PATH" pane release-agent "$INNOV_PANE_ID" \
  --source custom:my-agent \
  --agent my-agent
```

Only report when `INNOV_ENV=1` and the required variables are present so the integration remains a no-op outside Innov. Keep `--source` stable and unique to the integration. If reports can arrive out of order, include a strictly increasing `--seq`; Innov ignores stale sequence numbers from the same source.

You can include `--agent-session-id` or `--agent-session-path` with `report-agent`, or use `pane report-agent-session` when session identity changes independently of state. Innov exposes that reference through its pane and agent APIs. Automatic session restore additionally requires Innov to know how to launch that agent and resume the referenced session.

Use `INNOV_BIN_PATH` and the CLI wrappers for portable integrations. Code that needs direct IPC can send the equivalent `pane.report_agent`, `pane.report_agent_session`, and `pane.release_agent` requests described in the [Socket API](/docs/socket-api/#agent-state-reporting).

[Prime Agent's built-in Innov reporter](https://github.com/PrimeIntellect-ai/prime-agent/blob/main/packages/coding-agent/src/core/extensions/builtin/innov-agent-state.ts) is a real-world example. It activates only inside Innov, maps agent events to `working`, `idle`, and `blocked`, preserves report ordering across sessions, and releases authority on exit.

Some integrations report native agent session references. Innov uses official session references to resume Claude Code, Codex, Devin CLI, Droid, Kimi Code CLI, Qoder CLI, Cursor Agent CLI, Grok CLI, GitHub Copilot CLI, Pi, OMP, Hermes Agent, OpenCode, Kilo Code CLI, MastraCode, and Antigravity CLI panes after a Innov server restart unless `[session] resume_agents_on_restore = false` disables it.

Native session restore requires current Innov integrations: Pi integration version `2`, OMP version `3`, Claude Code version `6`, Codex version `5`, GitHub Copilot CLI version `2`, Devin CLI version `2`, Droid version `2`, Kimi Code CLI version `3`, Qoder CLI version `2`, Cursor Agent CLI version `1`, Grok CLI version `1`, OpenCode version `5`, Kilo Code CLI version `1`, Hermes Agent version `2`, MastraCode version `1`, or Antigravity CLI version `1`. Check installed versions with `innov integration status`.

## Pi

Install the Pi integration:

```bash
innov integration install pi
```

Innov writes the bundled extension to:

```text
~/.pi/agent/extensions/innov-agent-state.ts
```

If `PI_CODING_AGENT_DIR` is set, Innov writes to `$PI_CODING_AGENT_DIR/extensions/innov-agent-state.ts` instead. Innov creates the extensions directory when the Pi agent directory already exists. Uninstall removes only that extension file.

## OMP

Install the OMP integration:

```bash
innov integration install omp
```

Innov writes the bundled extension to:

```text
~/.omp/agent/extensions/innov-omp-agent-state.ts
```

Innov uses `PI_CODING_AGENT_DIR` as the complete agent directory when set. Otherwise, it uses `$HOME/$PI_CONFIG_DIR/agent` when `PI_CONFIG_DIR` is set, falling back to `~/.omp/agent`. If Pi and OMP resolve to the same extension directory, Innov refuses the OMP install so the OMP extension cannot be loaded by Pi. Configure separate agent directories before installing both integrations. Innov creates the extensions directory when the resolved OMP agent directory already exists. Uninstall removes only that extension file.

The OMP integration reports `omp` as the agent label, lifecycle state, and native session identity through Innov's socket API. It does not require native process detection for the `omp` executable, and Innov can resume an OMP pane with `omp --resume=<session>` after a server restart.

## Claude Code

Install the Claude Code hook:

```bash
innov integration install claude
```

The hook reports Claude Code session identity to the local Innov socket on session start. Claude Code state comes from Innov's screen manifest detection.

Innov uses `~/.claude` by default, or `CLAUDE_CONFIG_DIR` when set. The Claude config directory must already exist. Install writes `hooks/innov-agent-state.sh` and updates `settings.json` with Innov hook entries. Uninstall removes the matching hook entries and deletes the hook script.

## Codex

Install the Codex hook:

```bash
innov integration install codex
```

The Codex hook reports session identity through the same local socket API used by other integrations. Codex state comes from Innov's screen manifest detection.

Innov uses `~/.codex` by default, or `CODEX_HOME` when set. The Codex config directory must already exist. Install writes `innov-agent-state.sh`, updates `hooks.json`, and ensures `[features] hooks = true` in `config.toml`. It also removes the deprecated top-level `codex_hooks` flag when present. Uninstall removes Innov entries from `hooks.json` and deletes the hook script, but leaves `config.toml` unchanged.

## Devin CLI

Install the Devin CLI hook:

```bash
innov integration install devin
```

The hook reports native session identity from Devin session, prompt, tool-use, permission, and stop events. Devin state still comes from Innov's screen manifest and OSC detection because Devin hooks do not emit a reliable state transition after every permission cancellation or user interrupt.

Innov uses `~/.config/devin` by default, or `$XDG_CONFIG_HOME/devin` when `XDG_CONFIG_HOME` is set. The Devin config directory must already exist. Install writes `innov-agent-state.sh` and updates `config.json` with Innov hook entries. The hook refreshes the session reference while Devin runs. Uninstall removes Innov entries from `config.json` and deletes the hook script.

Innov resumes stored Devin sessions with `devin --resume <id>`. Native screen manifest detection remains the state authority whether or not the hook is installed.

## Antigravity CLI

Install the Antigravity CLI hook:

```bash
innov integration install antigravity-cli
```

Innov uses `~/.gemini/config/` by default, or `ANTIGRAVITY_CLI_CONFIG_DIR` when set. This is the directory Antigravity CLI reads global customizations from, and it must already exist. Install writes `hooks/innov-agent-state.sh` (or `innov-agent-state.ps1` on Windows) and adds a Innov-owned `innov` block to `hooks.json`. Antigravity CLI keys `hooks.json` by hook name, so install rewrites only that block and leaves other named hooks untouched. Uninstall removes the `innov` block and deletes the hook script.

This integration is session-only. It reports the conversation the pane is running and does not report agent state, so Innov keeps deriving working, idle, and blocked from what Antigravity CLI draws on screen.

The hook runs on `PreInvocation`, so Innov learns the conversation once the first prompt is sent. From then on Innov can resume the pane with `agy --conversation <id>` after a Innov server restart.

## Grok CLI

Install the Grok CLI hook:

```bash
innov integration install grok
```

The hook reports session identity through Grok's `SessionStart` hook while Grok CLI runs inside a Innov pane. Grok state comes from Innov's screen manifest detection.

Innov uses `~/.grok` by default, or `GROK_HOME` when set. The Grok config directory must already exist. Grok merges every `hooks/*.json` file in that directory, so install writes a self-contained `hooks/innov.json` with the Innov `SessionStart` entry next to the `hooks/innov-agent-state.sh` script, and never edits other hook files. Uninstall removes exactly those two Innov-owned files.

After Grok emits a session start event, Innov can use the reported session id to resume the pane with `grok --resume <id>`.

## Custom status labels

Integrations report lifecycle state as semantic state only. For example, report an agent as `working` without adding display fields to the lifecycle report.

```bash
innov pane report-agent w1:p1 \
  --source custom:docs \
  --agent docs-bot \
  --state working
```

User hooks that run next to a Innov-managed integration should use metadata instead of `report-agent`. Metadata changes presentation without taking over the integration's `idle`, `working`, `blocked`, or session restore authority. `--agent` and `--applies-to-source` guard only presentation fields (`--title`, `--display-agent`, and `--state-label`). Token patches always apply; their reporter owns clearing or TTL refresh. `--display-agent` changes the visible name.

```bash
innov pane report-metadata "$INNOV_PANE_ID" \
  --source user:claude-title \
  --agent claude \
  --title "Refactor auth middleware" \
  --display-agent "Claude: auth" \
  --token summary="refactor auth" \
  --state-label working="refactoring auth" \
  --ttl-ms 3600000
```

Tokens and state labels are visual-only. Waits, notifications, and workspace rollups still use the semantic state.

## Debug integration state

List known agents:

```bash
innov agent list
```

Read a pane when you need to verify what Innov can see:

```bash
innov pane read w1:p1 --source recent --lines 50
```

If integration state looks wrong, first confirm the agent is running inside Innov and that the relevant hook or plugin was installed for the same user account.
